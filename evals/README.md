# 评测样例

这里的 10 条评测**不测文采，测方法有没有被执行**：该发散的时候有没有发散、动作稿有没有写单元数、素材标签对不对得上、遇到冲突会不会静默绕开。

它对应 [SKILL.md](../SKILL.md) 里「阶段—产物—过关标准」那张表。每条带 `stage` 字段，标明它守的是哪一步。

## 怎么用

**方式一：人工逐条过。** 把 `prompt` 原样发给装了本技能的环境，拿回复对照 `expectations` 逐条打勾。

**方式二：让另一个模型当裁判。** 把 `prompt`、`expected_output`、`expectations` 和被测回复一起交给一个独立模型，让它逐条判 PASS/FAIL 并说明依据。裁判模型不要用同一个会话，否则会替自己辩护。

**方式三：改动后抽查。** 改了 SKILL.md、模板或 lint 规则之后，挑 `stage` 对应的 2–3 条重跑，确认没有把原有行为改坏。

## 打分

- 每条 `expectations` 只有「做到／没做到」两种结果，不打分。
- 全部做到 = PASS；缺任意一条 = FAIL，并在下面记一句「缺哪条、原文长什么样」。
- 连续两条 FAIL 指向同一处，说明是方法或措辞的问题，回去改 SKILL 或对应方法册，而不是改评测。

记录格式（复制到本地笔记即可，不必入库）：

```
日期 | 评测 id | PASS/FAIL | 缺的条目 | 备注
```

## 边界

- **没有自动评分。** 判定靠人看或模型当裁判，所以它不是 CI 门禁，是验收清单。要自动化得另写 judge，成本比这些样例本身高。
- **只覆盖行为。** 画面好不好看、打得对不对、身份会不会漂，仍需看片；那部分由 `scripts/motion-audit.py`、`scripts/fight-metrics.py` 和人工核对承担。
- **不是越多越好。** 发现新的「该做没做」再补一条；同一条纪律不要拆成五条写。

## 加一条新评测

在 `evals.json` 的 `evals` 数组里加一项，字段：`id`（kebab-case）、`stage`（1–6）、`prompt`、`expected_output`、`expectations`（至少 3 条，每条都是可判定的陈述）、`files`（需要附带的素材，通常为空）。

`python scripts/test_scripts.py` 会校验结构：id 不重复、stage 在 1–6、expectations 不少于 3 条。
